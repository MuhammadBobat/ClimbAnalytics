# DECISIONS.md — Decision Log

**Purpose:** every design/methodology decision that isn't purely mechanical gets an entry here, with its source. This file *is* the working draft of your dissertation's methodology chapter — write entries as if a reader outside your head needs to understand why you did something, not just what.

**Why this file instead of scattered comments or chat history:** chat history disappears between Claude Code sessions and doesn't survive to your write-up; comments in code get lost/buried as files are refactored; this file is the single durable, searchable, chronological record. Code comments should reference an entry ID here (e.g. `# see DECISIONS.md D-004`) rather than duplicating the full reasoning inline.

**Maintenance rule (also stated in `CLAUDE.md`):** any time a threshold, model, algorithm, or methodological choice is made — by you or by Claude Code — add an entry here *in the same session*, before moving on. Retroactively reconstructing "why did I pick 0.5s" six months later, from memory, is exactly what this file prevents.

## D-003: Four-state motion detection method — z-score thresholding, not cusum
**Date:** 2026-07-27
**Decision:** Detect per-joint moving/static state via z-score thresholding on the velocity signal (adapted from RGB video, not IMU), not Boulanger's original cusum-based statistical change-point method.
**Rationale:** Boulanger's cusum method requires a supervised learning phase with manually annotated climbs to construct per-sensor statistical models — this reintroduces the exact manual-annotation burden the project is scoped to avoid. The z-score approach is self-calibrating per clip (uses the clip's own mean/std) and requires no training set.
**Source(s):** Boulanger, J., Seifert, L., Hérault, R. & Coeurjolly, J-F. (2015). "Automatic Sensor-Based Detection and Classification of Climbing Activities." IEEE Sensors Journal 16(3), 742–749 — Section III-A (cusum method, learning-phase requirement) and Section IV-A (four-state definitions, reused verbatim in this project). Beltrán, R., Richter, J. & Heinkel, U. — method referenced in Beltrán, Richter, Köstermeyer & Heinkel (2023) "Climbing Technique Evaluation by Means of Skeleton Video Stream Analysis," Sensors 23, 8216 — describes standard-score (z-score) motion segmentation on RGB-derived joint velocity signals as the detection technique adopted here.
**Status:** proposed
**Addendum (2026-10-04):** Directly confirmed from Beltrán et al.'s own methodology text (Section 4.5, not a search snippet this time): "The technique used is based on a *standard score* on the joint velocity signal sampled at each frame," with the z-score given in their Eq. 9 as `z = (v − μ) / σ` — matches this entry's description exactly, closing the "grounded in a search snippet, not a full read" gap previously flagged. One refinement worth noting for D-004, not yet adopted: Beltrán et al. don't use a simple crossover of the z-score signal against `threshold_z`; they additionally compare the resulting n-σ graph against 50% of its own peak value, specifically to filter out detection-noise jitter before calling a phase transition. Flagging as a candidate refinement if D-004's empirical sweep finds the plain crossover too flicker-prone — not implemented now, just noted so it isn't lost.
**Source(s) confirmed via:** Beltrán, R., Richter, J., Köstermeyer, D. & Heinkel, U. (2023). "Climbing Technique Evaluation by Means of Skeleton Video Stream Analysis." Sensors 23(19), 8216. [PMC10574944](https://pmc.ncbi.nlm.nih.gov/articles/PMC10574944) — Section 4.5, Eq. 9.

## D-004: Threshold and duration values — empirical sweep methodology
**Date:** 2026-07-27
**Decision:** All threshold and minimum-duration values in this project (z-score threshold for motion detection, hysteresis duration for state-flicker suppression, occlusion tier boundaries) will be determined by sweeping a small candidate range on real test footage and selecting the value that best matches independently judged (by the author, as an experienced climber) ground truth — not asserted from theory.
**Rationale:** this mirrors the only concrete precedent found in the literature for this exact type of decision.
**Source(s):** Maschek & Schedl (2025) determined their 0.5-second hold-usage confirmation threshold by empirically testing durations between 0 and 2 seconds and selecting the best-performing value — same methodology, note this is a precedent for *how to choose a threshold*, not a value reused directly, since their threshold solved a different problem (hold-usage confirmation, which this project does not implement — hold detection is out of scope, see `PROPOSAL.md` §7).
**Status:** proposed — actual swept values to be logged as sub-entries once footage is available (e.g. D-004a for the four-state z-score threshold, D-004b for hysteresis duration).

## D-005: Whole-body CoM as primary tracked quantity
**Date:** 2026-07-27
**Decision:** Track whole-body centre of mass as the central performance-related quantity, computed as a weighted average of tracked joint positions (weighting scheme: TBD, see follow-up).
**Rationale:** both key sources treat pelvis/CoM motion as the structurally central variable in climbing movement analysis, not an incidental one — Boulanger's entire four-state framework is defined by pelvis motion crossed with limb motion; the JFMK biomechanics review lists "Center of Mass Shift" as one of five fundamental climbing principles and reports an empirical association between low CoM-to-wall distance and competition ranking.
**Source(s):** Dech, S. & Kittel, R. (2026). "Biomechanical Principles and Techniques — A Systematization for Sport Climbing." J. Funct. Morphol. Kinesiol. 11, 103 — Section 3.1.3 (Principle of Center of Mass Shift), citing Werner, Gebert & Kauer (1999) on CoM-distance vs. competition rank. Sibella, F., Frosio, I., Schena, F. & Borghese, N.A. (2007). "3D analysis of the body center of mass in rock climbing." Human Movement Science 26(6), 841–852 — cited by both Boulanger (2015) and Dech & Kittel (2026) as the direct precedent for CoM as a climbing-specific measurement.
**Status:** proposed
**Follow-up required:** decide and log exact joint-weighting scheme (full anthropometric segment-mass model vs. simplified proxy) once implementation begins — see `ARCHITECTURE.md` §4.3.

**Follow-up (2026-10-28) — CoM weighting scheme: trunk-centroid proxy**
**Decision:** Until a cited segment-mass table is chosen, CoM is computed as a trunk-centroid PROXY: equal weights (1.0 each) on `left_shoulder`, `right_shoulder`, `left_hip` and `right_hip`, i.e. CoM = (hip midpoint + shoulder midpoint) / 2, in 2D pixel space. Implemented as `metrics.compute_com`, with the weights held in a table (`TRUNK_CENTROID_PROXY_WEIGHTS`) so a different table can replace it. Exact weights: `{left_shoulder: 1.0, right_shoulder: 1.0, left_hip: 1.0, right_hip: 1.0}`. This is a proxy, not whole-body CoM: it ignores the head, arms and legs, so it will not reflect limb-driven CoM shifts, and it must be called a proxy in any write-up.
**Missing joints:** CoM is `None` at any frame where any of the four joints is a gap (no renormalisation). Gap-filling is left to `occlusion_handling.py` (D-007), not yet built.
**Rationale:** `ARCHITECTURE.md` §4.3 permits a simplified proxy if its exact weights are logged. §4.3 gives hip midpoint, shoulder midpoint and head as its example proxy; this one omits the head because the nose had 4 gap events (30 low-confidence frames) across the 5 own-footage clips, against 0 for each of the four trunk joints (events = runs of consecutive detected frames with confidence < 0.5, whole-frame drops excluded; recounted directly from `validation/output/*_keypoints.csv` on 2026-10-28), and renormalising over a missing joint makes the estimate jump. The COCO-17 output also has no head-top, neck, pelvis, hand or foot points, and no segment-mass table is cited in this repo, so a full segment model cannot yet be built without inventing numbers.
**Source(s):** no literature source for these weights — engineering heuristic, validate empirically. (D-005's sources support CoM as the tracked quantity, not this proxy.)
**Status:** proposed
**Open:** whether the proxy tracks whole-body motion adequately on own footage is untested. Planned check: compare the proxy to a segment-model CoM with a cited mass table on the same clips, reporting the change in velocity, state fractions and LDLJ.

**Follow-up (2026-10-28) — segment-model CoM (de Leva 1996), next to the proxy:**
**Decision:** Add a whole-body segment-model CoM to `metrics.py` (`compute_com_segment_model`), with the trunk-centroid proxy above kept unchanged as the baseline. CoM = Σ m_s · CM_s / Σ m_s over 14 segments; a segment with two endpoints has CM_s = P_prox + r_s (P_dist − P_prox), a point-mass segment sits at its keypoint. Source: de Leva, P. (1996), "Adjustments to Zatsiorsky-Seluyanov's segment inertia parameters", J Biomech 29(9):1223-1230 (printed identifier 0021-9290(95)00178-6), Table 4 (p. 1228): mass as % of body mass, CM position as % of segment length from the proximal end, male and female. The values were read from the PDF (local copy outside the repo, SHA-256 685916ec701cd860ab861b1901e27a90f946199c221b23acedebfb9a7dc72811) and checked against a secondary data file: all matched. Segment parameters used, male / female (mass % ; CM % from proximal end): head 6.94 / 6.68 (mass only, at the ear midpoint); trunk 43.46 / 42.57 ; 43.10 / 37.82 (MIDS-MIDH row: mid-shoulder-joint to mid-hip-joint, shoulder midpoint to hip midpoint); upper arm 2.71 / 2.55 ; 57.72 / 57.54 (shoulder to elbow); forearm 1.62 / 1.38 ; 45.74 / 45.59 (elbow to wrist); hand 0.61 / 0.56 (mass only, at the wrist); thigh 14.16 / 14.78 ; 40.95 / 36.12 (hip to knee); shank 4.33 / 4.81 ; 43.95 / 43.52 (knee to ankle, the KJC-AJC alternative-endpoints row, not the table's first-part KJC-LMAL row); foot 1.37 / 1.29 (mass only, at the ankle). Left and right segments use the same parameters.
**Approximations (every one):**
1. COCO-17 keypoints are not defined as joint centres; their offset from the paper's SJC, EJC, WJC, HJC, KJC and AJC is not measured here.
2. Trunk: the MIDS-MIDH row is used because its endpoints match the shoulder and hip keypoints. The paper notes that MIDS can be less accurate for locating the trunk CM when the shoulder joints move relative to the chest (it prefers a cervicale or suprasternale endpoint), which the author states is common in climbing. COCO-17 has neither alternative endpoint.
3. Head: the paper's head endpoints (vertex, mid-gonion) are not in COCO-17, so the head mass is placed at the ear midpoint and the head CM fraction is not used.
4. Hand and foot mass sit at the wrist and ankle keypoints. From the table (male): the hand CM is 79.00% of an 86.2 mm WJC-MET3 segment (about 68 mm beyond the wrist) and the foot CM is 44.15% of a 258.1 mm HEEL-TTIP segment (about 114 mm from the heel, which is not at the ankle); both offsets are neglected.
5. 2D pixel-space projection under D-008 and D-013; foreshortening of segments is not corrected.
6. Sex: male is the primary table because the current footage is male (author's statement); `sex` is a required argument, and a later product would take it as an input. Female and "mean" (an unweighted average of the male and female tables, a logged approximation) are sensitivity checks only.
7. Source population: college-aged Caucasian samples (100 male, 15 female, mean ages 24 and 19); applicability to the climbers is untested.
8. The source's mass percentages are rounded: male sums to 100.00%, female to 99.99%; weights are normalised by their sum.
9. Missing joints: the CoM is None whenever any of the 14 required joints (both shoulders, elbows, wrists, hips, knees, ankles and ears) is a gap, with no renormalisation. Nose and eyes are not used.

The comparison (`evaluation/2.2b/compare_com_models.py`) runs ONLY on frames where both models are defined (5,349 of 5,886); the 479 frames where only the proxy is defined are reported separately (`n_only_proxy_defined`) and are not compared. ## D-006: Smoothness metric — Log Dimensionless Jerk (LDLJ)
**Date:** 2026-07-27 (formula verified 2026-07-27, superseding the earlier unverified version of this entry)
**Decision:** Use LDLJ as the primary smoothness metric, applied to CoM velocity as the default signal. Formula:
```
LDLJ = -ln( (t2 - t1)^3 / v_peak^2  ·  ∫_{t1}^{t2} |d²v/dt²|² dt )
```
**Rationale:** LDLJ is the most established/widely used smoothness metric in the movement-science literature; different smoothness metrics can disagree, even in direction, on the same movement (e.g. one comparison study found LDLJ, NARJ, and zero-crossing count judged backward movements smoother while SPARC found the opposite), so picking one defensible, well-documented metric and stating the choice explicitly is preferable to an ad hoc formula.
**Source(s):** Originally developed by Balasubramanian, S., Melendez-Calderon, A., Roby-Brami, A. & Burdet, E. — cited as the standard reference across the secondary sources below. Formula (including the previously error-prone cubed duration term) confirmed directly via: Gulde, P. & Hermsdörfer, J. (2023). "Corrigendum: Smoothness metrics in complex movement tasks." Frontiers in Neurology, DOI: 10.3389/fneur.2023.1279682 — a corrigendum to Gulde & Hermsdörfer's own article, reported as correcting a missing `^3` term in an LDLJ formula; its exact corrected form is not confirmed (see the 2026-10-28 correction below). Cross-checked against: a comparison study (Sensors 23(3), 1158, 2023) computing LDLJ via "the Python code provided by Balasubramanian et al." on upper-limb movement data. **Primary-source identity — confirmed 2026-10-04:** Balasubramanian, S., Melendez-Calderon, A., Roby-Brami, A. & Burdet, E. (2015). "On the analysis of movement smoothness." *Journal of NeuroEngineering and Rehabilitation* 12:112. DOI: [10.1186/s12984-015-0090-9](https://doi.org/10.1186/s12984-015-0090-9). [Imperial Spiral record](https://spiral.imperial.ac.uk/entities/publication/0140ac66-2946-4c82-a1c3-fc546c8cb6f1) — title, journal, volume, year, and full author list confirmed directly, matching the "likely" venue guessed in the original version of this entry. This closes the identity question — confirmed to be the same paper referenced across the secondary sources below, not a different Balasubramanian smoothness paper.
**Honest limit of this check:** the exact formula *text* inside the primary PDF itself could not be independently re-read in this session — every mirror tried (PMC, HAL/Sorbonne, BioMedCentral) returned a reCAPTCHA wall, a 403, or a rate limit rather than article text. The formula above still rests on the two secondary-source cross-checks already in this entry (the Frontiers corrigendum, and the Sensors comparison study's re-implementation of "the Python code provided by Balasubramanian et al."), not a fresh primary read. **Correction (2026-10-28):** an earlier version of this paragraph said the Frontiers corrigendum corrects an error in Balasubramanian et al.'s own published formula. That was wrong: the Gulde & Hermsdörfer corrigendum corrects their own article, not Balasubramanian et al. (2015). Balasubramanian's Eq. 2 prints (t2−t1)^5; the dimensionally consistent form for a speed profile is (t2−t1)^3 / v_peak^2 (the author's own dimension check, not a published confirmation). The corrigendum's exact form is **not confirmed** — it has not been read directly. Narrower than "verified against primary text" — state that distinction if this is cited in the methodology chapter.
**Status:** implemented (LDLJ with the cubed duration term, and SPARC; unit-tested on synthetic profiles; not yet run on any clip)

## D-007: Occlusion handling — three-tier framework
**Date:** 2026-07-27
**Decision:** Adopt the three-tier occlusion framework in `ARCHITECTURE.md` §3 (cubic spline < 5 frames; Kalman filter 5–20 frames; root-lock + CoM substitution > 20 frames).
**Rationale:** single fixed-camera 2D tracking will have frequent occlusion (hands behind torso, limb crossing) — this is a known, literature-confirmed failure mode for climbing pose estimation specifically, not a hypothetical edge case.
**Source(s):** the three-tier structure itself is an original design for this project — **no direct literature source**, validate empirically. The underlying occlusion problem is confirmed by: Maschek & Schedl (2025), Results section — "longer occlusions of the hands behind the climber's upper body frequently led to detection inaccuracies." Cheng, Y., Yang, B., Wang, B., Yan, W. & Tan, R.T. (2019), "Occlusion-Aware Networks for 3D Human Pose Estimation in Video", ICCV 2019 — supports the confidence-gating principle only; see the 2026-10-28 addendum below for exactly what it does and does not support.
**Status:** proposed — not yet validated against real occlusion events.

**Addendum (2026-10-28):** Cheng et al. (ICCV 2019) support the principle behind confidence-gated gap detection: low-confidence keypoints are treated as missing rather than trusted, and occlusion can persist over many frames. They do not support the specific tier boundaries (<5, 5-20, >20 frames) or the fill methods (spline, Kalman, root-lock), which remain an original design. They fill gaps with a trained temporal network on 3D data, a different method. The boundaries are validated only by the planned hide-and-fill occlusion test.

- Whole-frame drops: 2 events (2 frames in `IMG_2412`, 1 frame in `IMG_2420`).
- Joint-level events: 29 — 19 under 5 frames, 9 of 5–20 frames, 1 over 20 frames (29 frames, 0.967 s, right ankle, `IMG_2412`, frames 10–38; it does not touch a clip boundary). 5 of the 9 mid-length events touch a clip boundary.

## D-011: ViTPose-L implementation route — HuggingFace `transformers`, not `mmpose`, plus YOLOv8n as the upstream bounding-box source
**Date:** 2026-07-27
**Decision:** Implement ViTPose-L via the HuggingFace `transformers` library (`VitPoseForPoseEstimation` + `AutoImageProcessor`, checkpoint `usyd-community/vitpose-plus-large`) rather than OpenMMLab's `mmpose`/`mmcv`. Pair it with YOLOv8n (`ultralytics`, COCO-pretrained, person class only, boxes only — not YOLOv8-**pose**) purely as the upstream person-bounding-box source, since ViTPose is a top-down method requiring an external detector (D-002).
**Rationale:** `mmpose`'s dependency stack (`mmcv`, `mmengine`, `mmdet`) requires version-matched, sometimes platform-compiled wheels and has a known history of fragile installs, particularly on newer Python versions and non-Linux/non-CUDA platforms. This project's dev environment is Python 3.14 on Apple Silicon (arm64, CPU-only, no CUDA) — well outside `mmcv`'s well-tested combinations — so `mmpose` was not attempted. `transformers`' ViTPose implementation is pure PyTorch with no compiled extensions and was installed and validated directly (see Status). For the person-bbox detector, the model card's own example uses RTDetr (`PekingU/rtdetr_r50vd_coco_o365`, ~166MB), but YOLOv8n (~6MB) is far cheaper per-frame on CPU and sufficient for the single-box-per-frame selection heuristic in `ARCHITECTURE.md` §2 — this is a substitution of detector, not of the ViTPose model itself, and is **not** the documented YOLOv8-**pose** fallback (that fallback is for replacing ViTPose's keypoint estimation entirely, not invoked here).
**Source(s):** no literature source — engineering/environment decision. Confirmed directly in this project's dev environment on 2026-07-27: `transformers` 5.14.1, `torch` 2.11.0 (CPU-only), `ultralytics` 8.4.108; `usyd-community/vitpose-plus-large` downloaded and loaded successfully (434M parameters); `yolov8n.pt` downloaded and loaded successfully.
**Status:** implemented — dependency install and model load validated in-environment. This is *not* the same as D-002a (accuracy replication against own footage), which still requires test clips and remains outstanding.
**Addendum (2026-07-27, found via smoke test, not docs):** `vitpose-plus-large` is a mixture-of-experts checkpoint (6 expert heads: COCO validation=0, AIC=1, MPII=2, AP-10K=3, APT-36K=4, COCO-WholeBody=5) and the forward pass raises `ValueError` unless an explicit `dataset_index` tensor is passed. `dataset_index=0` (COCO) is used throughout `validation/validate_vitpose.py`. This was not obvious from the model card's basic usage example (which uses the non-MoE `vitpose-base-simple` checkpoint) — only surfaced by actually running inference end-to-end, confirming it's worth doing that rather than trusting a paraphrased doc summary.

## D-013: Cross-session scale calibration — open question, needed before attempt comparison is built
**Date:** 2026-08-02
**Decision:** Not yet decided. Flagging that the whole-climb attempt-to-attempt comparison feature (`PROPOSAL.md` §6) likely needs some form of pixel-to-real-world scale calibration before its metrics are meaningful, since two filming sessions of the "same" perpendicular setup won't have the camera at exactly identical distance/position from the wall each time. ## D-014: tIoU as the planned metric if quantitative evaluation (D-010) is picked up
**Date:** 2026-08-02
**Decision:** If/when the deferred quantitative evaluation in D-010 is pursued, use temporal Intersection-over-Union (tIoU) as the primary metric for scoring how well the four-state classifier's timing matches ground truth — not just whether a state was detected at some point, but whether it was detected during the correct frame range.
**Rationale:** tIoU is a standard, well-precedented metric for exactly this kind of "did the detected time range match reality" question in activity/state recognition, and gives a graded temporal-alignment score rather than a coarse yes/no.
**Source(s):** Maschek & Schedl (2025) — tIoU formula (`|Tp ∩ Tg| / |Tp ∪ Tg|`) and its use alongside accuracy/precision/sensitivity, both at a 0.0 and 0.5 tIoU threshold, to separately capture "was it detected at all" vs. "was the timing right." Originally from Heilbron et al. (2015), "ActivityNet," cited by Maschek & Schedl as the source of the tIoU metric in activity recognition generally.
**Status:** proposed — dependent on D-010 being promoted from deferred to active; no action needed until then.

## D-015: Known-groups validation as a supplementary check for threshold selection
**Date:** 2026-10-04 (reconstructed — `ARCHITECTURE.md` §7 already referenced this entry by ID, but it was never actually written up here; writing it now from that section's own text rather than leaving the reference dangling)
**Decision:** Treat "known-groups validation" as a supplementary validity check for the four-state classifier's threshold selection (D-004), run alongside — not instead of — the qualitative evaluation already committed to in D-010. Method: group test clips by self-reported climber experience level, compute two per-clip summary stats from the four-state timeline (`% time pelvis-immobile` vs. `pelvis-moving`; `% time in Hold Interaction`, used as an approximate proxy for an exploratory/performatory split), and check whether the pattern across experience groups goes in the literature-predicted direction. The `threshold_z` value that produces the cleanest such separation is adopted — this doubles as D-004's actual threshold-selection methodology, not a separate pass. Full I/O spec (per-clip inputs/outputs, suggested standalone script location) lives in `ARCHITECTURE.md` §7, not duplicated here.
**Rationale:** without ground-truth annotation (deferred under D-010), there is no way to directly score the four-state classifier's accuracy. "Known-groups validity" — checking whether a measure can distinguish between groups that theory predicts should differ — is a standard technique used generally in instrument validation for exactly this situation (no gold-standard criterion available). Applying it here gives a second, more structured line of evidence for picking `threshold_z`, on top of the author's own subjective judgement (which D-004 already relies on alone).
**Explicit limitation — state this honestly, do not gloss over it:** `% time in Hold Interaction` is used only as an approximate, convenience proxy for the exploratory/performatory movement distinction from the climbing motor-control literature associated with Seifert (co-author on Boulanger, Seifert, Hérault & Coeurjolly (2015), already cited in D-003). This project has **no validated operationalisation** linking "Hold Interaction" (pelvis immobile + ≥1 limb moving, per the four-state model) to the formal exploratory/performatory construct — the mapping is this project's own approximation for a plausibility check, not a claim that the two are the same measurement. Do not present a known-groups result as validating the exploratory/performatory distinction itself in the write-up.
**CoM-to-wall exclusion:** CoM distance-to-wall (a depth/z-axis quantity) is excluded from this check because it is not measurable at all with a single perpendicular 2D camera (D-008) — a hard consequence of the camera setup every metric in this project already works within, not a limitation specific to this check.
**Source(s):** "known-groups validity" as a general technique — no single climbing-specific source; standard concept in measurement/instrument validation methodology generally, applied here rather than taken from a climbing-specific precedent. The exploratory/performatory distinction traces to the climbing motor-control literature associated with Seifert; the specific mapping onto this project's Hold Interaction state is this project's own approximation, not sourced from a paper that defines it that way — flagged above, not hidden.
**Status:** proposed — not required for the core pipeline (`ARCHITECTURE.md` §1–§6); required as a prerequisite check before `threshold_z` (D-004) is finalised.

## D-016: Foot keypoints — ViTPose-WholeBody and MediaPipe both explored, staying on ViTPose-L body-only for now
**Date:** 2026-10-04
**Decision:** Confirmed ViTPose-L's current checkpoint cannot produce foot/toe keypoints, explored two routes to get them (ViTPose-WholeBody via `dataset_index`, and MediaPipe Pose as a second model), and decided to stick with ViTPose-L's standard 17-keypoint body output for now rather than adopt either. Foot placement/smoothness metrics are not currently in `PROPOSAL.md` scope (§3, §5) — this entry is a feasibility note for if/when that changes, not a scope change itself.

**Route 1 — `dataset_index=5` (the "COCO-WholeBody" MoE expert on `vitpose-plus-large`): does not work.** Verified directly that the model's decode head outputs exactly 17 heatmap channels (`[1, 17, 64, 48]`) regardless of which of the 6 expert indices (0–5) is passed — `dataset_index` only selects which backbone expert processes image features, it does not change the fixed output head, which this checkpoint always wires to standard COCO-17. Separately, and worse: confidence scores produced under `dataset_index=5` came out in the ~2.0–3.1 range instead of the expected [0,1] (e.g. `IMG_2412.MOV` mean_confidence 2.56 vs. 0.87 under index 0) — not merely lower-quality, but off-scale and unusable by every threshold in `validate_vitpose.py`, which assumes [0,1]. No checkpoint in the `usyd-community` HuggingFace `transformers` port exposes a true COCO-WholeBody (133-keypoint) decode head; that only exists in OpenMMLab's original `mmpose`-based ViTPose-WholeBody configs, and installing `mmpose`/`mmcv` to reach it reintroduces exactly the dependency fragility D-011 already ruled out on this Python 3.14 / Apple Silicon / no-CUDA environment (confirmed on 2026-10-04: `mmcv` 2.2.0, `mmpose` 1.3.2, `mmengine` 0.10.7 are all ~2 years stale on PyPI, built against PyTorch versions well behind this project's `torch` 2.11). `validate_vitpose.py`'s `VITPOSE_COCO_DATASET_INDEX` has been reverted to `0`.

**Route 2 — MediaPipe Pose (`mediapipe` package), separate model, exploratory only: works, but not adopted.** MediaPipe Pose has real heel/foot-index (toe) landmarks. A scratchpad-only script (not committed; not part of any module boundary) ran MediaPipe's "heavy" Pose Landmarker on `IMG_2412.MOV` (150 frames, CPU): mean visibility left_heel 0.780, right_heel 0.724, left_foot_index 0.667, right_foot_index 0.593 (min values as low as 0.192–0.339) — real foot tracking, but visibly weaker and noisier than ViTPose's body-joint confidence on the same footage (D-002a: ~0.87–0.90 mean, rarely below 0.5). Hit one unrelated but notable engineering snag along the way: `mediapipe` 1.0.x hard-crashes (native abort, not a Python exception) on macOS Apple Silicon specifically — confirmed upstream bug, [google-ai-edge/mediapipe#6356](https://github.com/google-ai-edge/mediapipe/issues/6356); pinning to `mediapipe==0.10.35` avoids it. Worth remembering if this is revisited: `mediapipe` must stay pinned to `0.10.35`, not left to float to latest.

**Why not adopt MediaPipe (even just for feet) right now:** two reasons, independent of the scope question. (1) D-002's own literature comparison already found MediaPipe meaningfully behind ViTPose on climbing footage generally (83.5% vs. 86.6% accuracy, and far more missing-detection frames — 150+ consecutive vs. 2–10), and today's foot-specific numbers don't contradict that pattern. (2) Running a second full model per frame alongside ViTPose-L is a real architecture and runtime-cost decision (every frame processed twice), not a drop-in addition — not something to fold in quietly alongside a pose-model validation session.
**Rationale:** both routes were evaluated with actual runs against real footage (not estimated), per CLAUDE.md rule 9. Decision to not adopt either is a scope/cost call, not a finding that either route is impossible — MediaPipe-for-feet specifically remains a live, validated-as-feasible option (modulo the version pin) if foot placement is later promoted into `PROPOSAL.md` scope, most likely as an augmentation (MediaPipe feet + ViTPose body) rather than a replacement, given ViTPose's clear edge everywhere else.
**Source(s):** direct experimentation in this project's environment, 2026-10-04 — `transformers`/`usyd-community/vitpose-plus-large` dataset_index sweep; `mediapipe` 0.10.35 Pose Landmarker ("heavy") on own footage; PyPI version check for `mmcv`/`mmpose`/`mmengine`; GitHub issue google-ai-edge/mediapipe#6356.

## D-017: Hold detection — hybrid gym-specific detector + colour-matching, superseding D-009
**Date:** 2026-10-04
**Decision:** Reverse D-009. Add a hold-detection component: (1) a single-class object detector ("hold" vs. background) fine-tuned from a pretrained **YOLOv8n** checkpoint (picked over YOLOv11n for consistency with the YOLOv8n already in use for person-box detection, D-011 — same library, same weights-management pattern, no new dependency) on hand-annotated frames from this project's own gym, to localise hold bounding boxes against lighting, climber occlusion, and background clutter; (2) classical HSV colour-matching, applied within each detected hold's bounding box against this gym's known route-colour palette, to assign each hold to a route/grade (this gym grades by hold colour). Detection (localisation) and colour-matching (classification) are kept as separate steps rather than training a multi-class detector, since colour-matching is cheap, interpretable, and needs no per-colour training examples.

**Why this reverses D-009's original reasoning:** D-009 ruled out hold detection specifically because of hand-annotation cost. ## D-018: Promote hold-relative feedback — contact timeline, hold-to-hold segmentation, and derived timing/foot/balance metrics
**Date:** 2026-10-07
**Decision:** Supersede the exclusion of hold-relative feedback written into `PROPOSAL.md` §7 and `ARCHITECTURE.md` §8's intro (D-017 alone — localisation plus colour/route assignment — gave static hold positions, not a per-hold interaction timeline; this entry adds the missing piece). Add to core scope, in this order of dependency:
1. **Keypoint-to-hold contact timeline** (`hold_contact.py`): for each frame, which hold each wrist/ankle keypoint is in contact with, aggregated into touch events `{hold_id, limb, start_frame, end_frame, route_label}`.
2. **Hold-to-hold segmentation of existing metrics:** CoM velocity/displacement, four-state fractions and LDLJ computed per interval between successive contact events, in addition to per clip. LDLJ needs a **minimum segment duration** below which it is not reported (value TBD — determine by the D-004 sweep methodology, do not assert one; segments flagged as dynamic moves should be reported with that context, since LDLJ's smoothness reading is not equivalent across static and ballistic moves).
3. **Timing metrics derived from the timeline (no new model):** climb time (first to last contact), pace (contact events per second), pre-climb pause (first frame with a detected climber to first contact), dwell per hold (contact duration), flight time (gap between a limb's release and its next contact).
4. **Foot usage ratio and foot readjustment count:** share of contact events made by ankles; a readjustment is a same-ankle release and re-contact on the same hold within a window (window TBD, empirical). Uses the ankle keypoints ViTPose-L already outputs; **no toe/fingertip keypoints** (D-016 stays on body-only — a foot keypoint change would be its own decision).
5. **Balance proxy:** horizontal offset of the CoM from the centre of the supporting contact points in the image plane (normalisation TBD).

**Real dependencies — not buildable today:** needs the four-state classifier calibrated (Phase 4) and the hold detector trained and colour-calibrated (Phase 0.5.2–0.5.5).

**Contact provenance rule:** each keypoint carries whether it was observed, interpolated (D-007 tier 1/2) or stale (tier 3). Contacts decided from tier-3 keypoints are recorded as **unknown**, not guessed, and each clip reports the share of its contact timeline that rests on observed or short-gap keypoints. The tier boundaries are themselves unvalidated heuristics (D-007), so contact accuracy inherits that uncertainty. Contact accuracy must be measured on own footage before any feature below is trusted (task 0.5.7).

**Known risks, stated up front:**
- Hold IDs depend on the per-clip layout merge in `ARCHITECTURE.md` §8.1 (sampled frames, IoU clustering); if that merge is noisy, IDs may not be stable enough for a clean timeline. Validate empirically.
- 2D proximity cannot distinguish a hand near a hold from a hand gripping it, and wrist/ankle keypoints are not the actual contact points. A 2026 preprint reports markedly better contact detection with fingertip/toe keypoints from a different pose model (Sapiens) than with wrist/ankle keypoints from ViTPose-L and YOLOv8-pose. Read only as a fetched summary, preprint status, not independently verified here; licence and compute cost unchecked. Treat as an open spike, not a decision.
- Foot readjustment (item 4) and the balance proxy (item 5) have **no literature source — engineering heuristics, validate empirically**. Do not present them as established measures.
- Feedback wording stays comparative/descriptive (D-010, D-015 limitations): none of these metrics is ground-truth validated as an indicator of climbing quality.

**Distance-to-wall is not replaced and remains out of scope:** it is a depth quantity not measurable with the D-008 single perpendicular camera (D-015). The in-plane items above (balance proxy, foot usage) are partial proxies for the same intent, not a measurement of it. Testing BlazePose z as a 2.5D route is a separate optional spike, not part of this decision.

**Rationale:** with hold detection in scope the per-hold timeline is the natural next layer, and segmenting the existing metrics by hold-to-hold interval makes feedback specific ("the move between holds 3 and 4") rather than whole-clip. It also reduces the LDLJ dyno problem by isolating a ballistic move in its own segment.
**Source(s):** Frontiers in Psychology (2020) climbing fluency study, DOI 10.3389/fpsyg.2020.00249 — climbing time and immobility ratio as fluency indicators (page read via fetch, first 100,000 of ~102,000 characters; authors and exact title **not yet confirmed — confirm before citing**). "Training-Free Hold-Usage Detection in Sport Climbing with Foundation Pose Models", arXiv:2609.30026v1 (preprint) — climb time, pace, dwell, foot-usage ratio and flight time derived from a hold-usage event stream. Boulanger et al. (2015) per-hold touch framing already cited in D-003. Items 4–5: no literature source, per above.

## D-019: Route auto-definition and route progress
**Date:** 2026-10-07
**Decision:** Do not require manual start/finish annotation. Derive the route from the hold layout (`ARCHITECTURE.md` §8.1) and the contact timeline:
- **Route membership:** holds whose colour-matched route label (D-017a) equals the route the climber touches, spatially clustered, selecting the cluster the climber contacts. This rests on the author's knowledge that same-colour problems do not overlap on this wall — **an assumption to validate on real footage**, not a tested fact.
- **Start holds:** the first one or two holds the climber touches (one hold if both hands go on the same hold).
- **Finish hold:** the topmost hold of the route cluster, assuming the climber completes the problem.
- **Route progress:** number or fraction of route holds touched, and the furthest hold reached; for a failed attempt it is reported as progress short of the finish, not as a finish.
The gym's own start/finish markers (small silver round metal tags) are **not** relied on: they are unlikely to be reliably visible to the detector.
**Known risks:** a missed hold shortens the route and overstates progress (detector recall must be measured); "furthest hold" by vertical position fails on traverses (ordering rule TBD — decide when hold_contact.py exists, log as an addendum); colour→route membership depends on HSV calibration (D-017a, task 0.5.5), and Ludford (2024) reported 72–88% colour classification accuracy (cited in D-009); "first touched" start holds depend on the contact timeline being correct at the start of a clip.
**Rationale:** avoids per-problem manual input, consistent with the hybrid detector's purpose (D-017).
**Source(s):** author's knowledge of own gym (2026-10-07). No literature source for the route-definition heuristics — engineering heuristics, validate empirically.
**Status:** proposed — blocked on D-018's dependencies. See 2026-10-21 addendum below (route-membership/start/finish/progress wording updated for the three-class segmentation detector, D-022).

**Addendum (2026-10-21) — route definition updated for the three-class segmentation detector (D-022):** this does not rewrite the decision above; it replaces the route-membership/start/finish/progress wording, which relied on the gym's silver start/finish tags and "topmost hold" without distinguishing hold classes. That wording predates D-022's `hold` / `descent_hold` / `volume` class split.
- **Route membership:** `hold`-class objects (D-022) of the route colour, spatially clustered, selecting the cluster the climber actually contacts. `volume` and `descent_hold` objects are excluded from route membership entirely — they are never route members and never the finish hold.
- **Start holds:** the first one or two holds touched by the climber's **hands** (one hold if both hands share it). Foot contacts do not count toward start.
- **Finish:** the topmost route-coloured `hold` touched by a hand, assuming the climb was completed.
- **Route progress:** the furthest route hold reached by hand, plus the count of route holds touched by hand.

- **No weights:** a lower weight for volume contacts was considered and rejected as unjustified — volumes don't count toward progress at any weight (per D-022's downstream-roles rule), rather than counting at a reduced one.

**Decision:** Ran as an isolated feasibility spike (`experiments/blazepose_z_spike/`, branch `spike/blazepose-z`), outside the runtime pipeline — not a pipeline change. **Findings, taken directly from `experiments/blazepose_z_spike/REPORT.md`:**
- **Detection rate:** BlazePose detected a pose in 100/100 frames on all 5 clips — it never lost a frame ViTPose-L caught (ViTPose-L itself: 98/100 on IMG_2412, 100/100 on IMG_2416/2417/2419, 99/100 on IMG_2420, per D-002a). The spike did not investigate the cause (candidates: occlusion, a body orientation BlazePose handles worse, or a genuine ViTPose-L error on that side — not distinguished).
- **Torso-lean z sign flips (100 frames per clip):** IMG_2412 13 (range -0.213 to 0.024), IMG_2416 5, IMG_2417 3, IMG_2419 2, IMG_2420 2. For IMG_2412 specifically, frames 10→11 were pulled and visually compared: the climber's pose was static between them, while torso_lean_z read `+0.00192 → -0.00053 → +0.00238` across frames 9–11 — sub-centimetre-scale noise crossing zero, not a real lean reversal. Reported as a direct observation on this one checked instance, not generalised to every flip in every clip.
- **Ankle z jitter during visually-stationary segments** (mean std, world-landmark units ≈ metres, hip-relative): mostly 0.02–0.05 across clips/ankles; one outlier, IMG_2419's right ankle at 0.104 (only 1 qualifying segment — a single short window, not a stable estimate). This characterises jitter only, not accuracy.
- **One supporting, non-systematic observation:** in one visually-checked `IMG_2412` frame where the hips were visibly pulled back from the wall while the feet stayed planted near it, both ankle-z-relative-to-hip values read clearly positive (`+0.20`, `+0.21`) — the qualitatively expected direction under MediaPipe's z-sign convention, from one frame, not a systematic validation.

- Only 100 frames per clip were tested, not full climbs.
- No ground truth exists, so everything above is internal consistency and agreement-with-ViTPose-L only — no real-world accuracy claim is supportable.
- The hypothesis as originally posed (while an ankle is planted, hip distance from the wall ≈ -(ankle z - hip z)) was **not validated** — no contact timeline existed in this spike to identify actual plant/release events, so only the narrower check (ankle z stability during *visually*-stationary segments) was run.

**Rationale:** per CLAUDE.md rule 9, every number above comes from code actually run against this project's own footage in `experiments/blazepose_z_spike/`, not estimated.

## D-022: Hold detector model — YOLOv8n-seg instance segmentation with polygon labels, three classes
**Date:** 2026-10-21
**Decision:** Change the hold detector's output type from bounding boxes to instance segmentation masks, and its class set from one (`hold`) to three. This supersedes only the box-output/single-class **wording** in D-017 — D-017's hybrid design (fine-tuned detector + classical HSV colour-matching) and its authorisation to proceed stand unchanged; only the model's output type and class set change.

Train one **YOLOv8n-seg** model (`ultralytics`), polygon-annotated in Roboflow using Smart Select, with three classes:
- `hold` — every real hold, including coloured volumes and holds mounted on volumes (each mounted hold is its own label; a coloured volume is itself labelled `hold`, since it carries a route colour).
- `descent_hold` — holds marked with red arrows, for downclimbing only.
- `volume` — grey volumes (large, always-on wall extensions, not route-specific).

**Context:** holds are often irregular in shape, so a bounding box's centre can fall off the hold itself, and a box necessarily includes background pixels around an irregular shape. That background contaminates both colour sampling (D-017a) and any future contact test (D-018) that checks proximity to the hold's actual extent rather than its box.

**Consequences:**
- HSV colour matching (D-017a) samples pixels **inside the mask**, not the bounding box.
- Contact tests (D-018) use the polygon as the contact region, not a box.
- Boxes, where still needed (e.g. the §8.1 IoU-merge step across sampled frames), are derived from each polygon's bounding rectangle rather than detected directly.

**Downstream roles:**
- `hold` objects can be route members (D-019).
- `volume` and `descent_hold` are never route members and never the finish hold.
- `descent_hold` is ignored in analytics entirely (contact timeline, route progress, metrics).
- Volume contacts are real physical contacts — logged in the contact timeline (D-018) like any other touch event — but they do not count toward route progress (D-019), since a volume carries no single route's colour and isn't part of any route's hold sequence.

**Annotation rule:** polygons only. A box-type label appearing in an exported segmentation file is a data error, not a valid `hold` label — see `training/check_seg_labels.py` below, written specifically because a real user export already contained two such lines mixed in with polygons.

**Evidence:** no literature source — engineering decision, validate empirically. No accuracy/mAP figure is given here; validation results are TBD pending training.

**Open questions, listed explicitly rather than silently assumed:**
- Whether YOLOv8n-seg is accurate enough on this gym's holds — to be checked against the box model (D-017) on a held-out split once both exist.
- Class index order — must be read from the Roboflow export's `data.yaml` at train/inference time, never assumed or hardcoded (same rule the new label-check script follows).
- How many `volume` examples exist in the annotated set — volumes are likely rarer than regular holds, so small-class performance is unknown until counted.

**Scope note:** `CLAUDE.md` rule 4 and `PROPOSAL.md` §3 previously described a "single-class" hold localiser; that wording is updated in both files to "one YOLOv8n-seg hold detector with three classes." This remains the same single narrow training exception D-017 already authorised — it is **not** permission to fine-tune the pose model or anything else.
**Rationale:** polygon masks match the geometry of real holds far better than axis-aligned boxes, and sampling colour only from inside the mask removes the background-pixel contamination a box would include. Both points are engineering reasoning about this specific change, not a sourced method — no new citation is claimed for them.
**Source(s):** no literature source — engineering decision, validate empirically. D-017's own sources (Reiff 2024, Ludford 2024, Maschek & Schedl 2025) remain the evidentiary basis for the underlying hold-detection approach; this entry changes output representation and class count only, not that basis.
**Status:** proposed

**Annotation rules (appended 2026-10-21):** label only holds on the wall actually being climbed, including small, blurry, or partly hidden ones — do not skip a hold just because it's hard to see if it's clearly part of the climbing wall. Do not label holds on background walls or adjacent walls visible in the same frame. Skip ambiguous cases (e.g. a hold where it's unclear which wall it belongs to) rather than guessing either way. Apply this rule consistently across every annotated image, not just the easy ones. No literature source — engineering decision, validate empirically.

**Open question (not decided, not implemented):** even with this annotation rule, the trained detector may still fire on background/adjacent-wall holds at inference time, since the rule only constrains training labels, not what the model generalises to. A per-setup climbing-wall region mask (manually or semi-automatically defined once per camera setup, to suppress detections outside it) may be needed to handle this. This is **not yet decided** — flagged here as an open question only; do not build a region-mask mechanism until a separate decision is made.

**Addendum (2026-10-21) — pixel-count tracking for mask-based colour sampling:** `DEFAULT_MASK_ERODE_PX` (5px, unvalidated placeholder) erodes every side of a detection's polygon mask before colour sampling. On a small hold this margin could leave only a handful of pixels without actually emptying the mask to zero — the existing `used_mask_erosion_fallback` flag only catches the zero-pixel case, so a noisy few-pixel reading would otherwise pass through silently. To make this visible, `hold_detection.py` now computes and records, for **every** detection regardless of class (not just `hold` — mask size is a property of the detection itself, useful for sanity-checking `volume`/`descent_hold` detections too), the full polygon-mask pixel count and the post-erosion pixel count. Both are written to the per-clip CSV (`mask_pixel_count`, `eroded_mask_pixel_count` columns) and summarised per class in the console output (minimum and median of each, not only the fallback count). **No "too few pixels" cutoff is set.** Any such cutoff is itself a threshold that should be chosen from real pixel-count data during 0.5.5's HSV calibration (same D-004/D-017c empirical-sweep methodology already used elsewhere in this project), not guessed now. When 0.5.5 happens, check the smallest holds' pixel counts specifically — that was the concrete motivation for this addendum.
**Source(s):** no literature source — engineering instrumentation, not a modelling decision.
**Status:** proposed (implemented in `hold_detection.py`); verified only against synthetic/hand-written polygon fixtures per `CLAUDE.md` rule 9 — no real pixel-count distribution exists yet, since no detector has been trained.

**Addendum (2026-10-28) — cut-off holds:** Annotate every hold that is partially cut off by the frame edge, as long as it is on the climbed wall. This extends the existing annotation rule (hold on the wall being climbed, including small, blurry or partly hidden ones); a hold does not get skipped because the frame edge cuts it. The polygon follows the visible part of the hold and runs along the frame edge. Cut-off holds can have small masks, so they interact with the mask-erosion margin and the pixel-count tracking above (a small or partial mask may fall back to the un-eroded mask); this is to be looked at in the pixel-count data once a detector exists. No literature source — engineering decision, validate empirically.
**Status:** proposed

**Addendum (2026-10-28) — overlapping polygons and keypoints inside several polygons:** A hold bolted on top of a larger hold or a volume gets its own polygon, drawn on top of the larger one (this restates D-022's "each mounted hold is its own label"; the larger object keeps its full outline and is not cut out around the hold). When a keypoint falls inside several polygons, the smallest polygon (by area) wins, so a wrist on a hold mounted on a volume is attributed to the hold, not the volume. This is a proposed rule for the contact test (D-018), to be checked at 0.5.7. It is consistent with the class-aware cross-frame merge in hold_detection.py, which already keeps an overlapping hold and volume rather than suppressing one. No literature source — engineering decision, validate empirically.
**Status:** proposed

## D-026: Candidate CoM estimators for step 2.2c — defined and compared, none adopted
**Date:** 2026-11-01
**Decision:** Define four estimators beside the trunk-centroid proxy (A, `compute_com`) and the full 14-joint segment model (F, `compute_com_segment_model`), all in `metrics.py`, and compare them on the five own clips (D-025's step 2.2c; `evaluation/2.2c/`). No estimator is adopted and none is ranked here; the proxy remains the working CoM. The final choice, if made, is a dated addendum to this entry with its own status (D-025 reserved "D-026" for the final choice; this entry is that one entry and D-025's text is unchanged). Male de Leva (1996) Table 4 throughout (as the D-005 follow-up).
- **B** (`compute_com_trunk_point`): B = (1 − w)·shoulder midpoint + w·hip midpoint, 0 ≤ w ≤ 1. w is fitted leave-one-clip-out over the five clips: for each held-out clip, w minimises the mean Euclidean position difference (pixels) between B and F, over the frames of the four other clips where F is defined (frames pooled, frame-weighted). Each clip's B uses the w of the fold in which it was held out. Torso-length differences are also reported. w per fold is in `evaluation/2.2c/output_full/loco_trunk_weight.csv`; no all-five-clip w is produced.
- **C** (`compute_com_segment_model_no_head`): F without the head (trunk, both arms, both legs; hands at wrists, feet at ankles), mass fractions renormalised to sum to 1. 12 joints (no ears).
- **D** (`compute_com_trunk_legs`): trunk and both legs only (thigh, shank, foot at ankle), renormalised. 8 joints.
- **E** (`compute_com_blended`): E = B + Σ m′_s·(CM_s − B) over the 12 limb segments (upper arms, forearms, thighs, shanks, hands, feet), m′_s the head-renormalised mass fractions. A segment is used only when every one of its joints has a position and a raw confidence at or above a cut-off (hand and foot: their single joint); otherwise its term is zero, so a lost limb falls back toward B. E is `None` only where B is `None`. Cut-off swept over 0.5, 0.6, 0.7, 0.8 and **not chosen**. Main E uses B at the fitted fold w.
- **E-dL**: the same E with w = de Leva's trunk CM fraction (0.4310 male), at the same four cut-offs. With every limb segment used, E-dL equals C exactly (unit-tested); with none used it is a trunk-CM point. Reported in the tables, not drawn in the overlays.
- **Enabling change:** `JointSeries` gets an optional `confidences` field (raw keypoint confidence, kept below 0.5 where the position is `None`), filled by `load_keypoints_csv`, carried by `apply_frame_exclusions`.
- **Measures compared** (per clip and pooled; definitions in `evaluation/2.2c/output_full/manifest.txt`): coverage; position difference to F on frames where both are defined (px and torso lengths); speed series; jitter J(t) = ‖p(t+1) − 2p(t) + p(t−1)‖ / L(t), torso lengths per frame² (L = shoulder midpoint to hip midpoint, no division by Δt²); defined-to-`None` transitions per 1,000 frames and the number of contiguous defined runs; for E, the mean number of limb segments used and use toggles per 1,000 frames.
**Approximations (every one):**
1. The D-005 follow-up list (items 1–9) that still applies: COCO-17 points are not joint centres; trunk = MIDS-MIDH row; hand and foot mass at wrist and ankle; 2D pixel projection (D-008, D-013); male table by the author's statement; college-aged source sample; rounded percentages.
2. Head removal (C, D, E): the head's mass (6.94% male) and its motion are not represented; the size of the effect on this footage is not measured here.
3. Renormalisation (C, D, E): dividing the kept fractions by their sum is equivalent to placing the removed mass at the CoM of the kept segments. Logged in `manifest.txt`: C and E limbs remove the head (removed 0.0694, kept 0.9306, scale 1/0.9306 = 1.074576); D removes the head, both upper arms, forearms and hands (removed 0.1682, kept 0.8318, scale 1/0.8318 = 1.202212); sums after are 1. For D this places the arms and head at the CoM of trunk and legs, which a climber with the arms overhead contradicts.
4. B: w is fitted to F, not to ground truth, so B inherits F's errors (D-025: jitter and dropouts in six of ten reviewed steps) and the fitted w absorbs the average limb offset, so it is not the trunk's own CM. The fit uses only frames where F is defined (all 14 joints at or above 0.5), pixels as the loss, frames pooled across training clips (frame-weighted, so the long clip weighs most), five clips of one gym.
5. E: the confidence is the pose model's heatmap score, not a calibrated probability, and a high score can sit on a wrong position (D-007 addenda: a confidently wrong keypoint is invisible to the gap statistics). Gating is binary, so E steps by m′_s·(CM_s − B) when a segment crosses the cut-off. "Falls back toward B" assumes B is a good fallback. With B at the fitted w, the limb terms are added on top of a B that already absorbed an average limb offset (double count when limbs are confident); E-dL is included to separate this. Trunk joints keep the D-007 0.5 rule, not the cut-off. A cut-off below 0.5 would behave as 0.5 because positions below 0.5 are already gaps.
6. E uses head-renormalised fractions (so E equals C when w is the trunk CM fraction and every joint passes); raw fractions would place the head mass on B.
7. All candidates are raw, unsmoothed and not gap-filled; a joint below 0.5 is a gap (D-007), and C, D and F are `None` where any required joint is a gap, with no renormalising over a missing joint. Revisit after 3.2 and 5.1a (D-025).
8. The comparison target is F, which has no ground truth; closeness to F is not accuracy. The jitter measure cannot separate estimator noise from real acceleration and is not a validity measure. "Common support" means all thirteen series defined, which is F's support.
9. The ten overlay windows (`evaluation/2.2b/output_full/top_speed_differences.csv`) were selected by proxy-versus-F speed disagreement (D-025); they over-represent F's problems.
10. Five clips of one gym, one fold per clip; the 2.2b exclusion list (IMG_2419 frames 597–614) applies.

**Addendum (2026-11-01) — primary source read; LDLJ and SPARC implemented in `metrics.py`:**
- **Primary source read.** The author supplied the PDF of Balasubramanian, Melendez-Calderon, Roby-Brami & Burdet (2015), *J NeuroEng Rehabil* 12:112 (local copy outside the repo, SHA-256 97758b3daac71bc637100caf0a43eedf204bfaa13debc105663c2b0847fdb257; received 16 June 2015, accepted 27 October 2015); I read the whole 11-page PDF. The Additional files (including Appendix A, the SPARC derivation, and Appendix B, the noise analysis) were not in it. Eq. 2 is printed as DLJ = −(t2 − t1)^5 / v_peak² · ∫|d²v/dt²|² dt, LDLJ = −ln|DLJ|, with v the speed. This confirms the 2026-10-28 statement above that the paper prints ^5. The paper's own requirement is that a valid measure be independent of amplitude and duration, i.e. dimensionless.
- **Exponent settled numerically.** `tests/test_smoothness.py` scales a minimum-jerk speed profile by amplitude k and duration m. With (t2 − t1)^3 the LDLJ is unchanged (differences ≤ 2e-15 for k = 3.7, m = 2.3). With (t2 − t1)^5 it shifts by exactly −2 ln m (−1.665818 for m = 2.3) and is independent of k, so the same invariance test fails; the two exponents coincide only when the duration is exactly 1 s, which hides the error. So ^3 is the dimensionally consistent form; the author's own dimension check of 2026-10-28 is now confirmed by computation. The Gulde & Hermsdörfer corrigendum's exact form is still unread. A single minimum-jerk bump gives LDLJ = −ln 204.8 analytically (the test checks the code against it).
- **Implemented:** `speed_profile`, `compute_ldlj(times, speeds)` and `compute_sparc(times, speeds, *, amp_threshold, omega_c_max, n_fft)`. Numerical choices (mechanical, not in the paper; listed so they are not hidden): second derivative of speed by two passes of `np.gradient` (central differences, second-order one-sided at the ends, real timestamps); integral by the trapezoid rule; the speed at frame t is the step t−1 → t (as `compute_velocity`); a window containing a gap returns `None` and is never bridged; no smoothing; SPARC assumes uniform sampling, fs = (N − 1)/(t_last − t_first); the adaptive cut-off on the grid is the frequency of the last point with normalised spectrum ≥ amp_threshold, capped by omega_c_max, and the arc length is the polyline through (ω/ωc, V̂) for grid points ≤ ωc (no interpolation at ωc when the cap falls between points).
- **SPARC parameters (answered by the author, same day).** `amp_threshold` (V̄), `omega_c_max` (rad/s) and `n_fft` stay required keyword arguments at every call site (no defaults in `compute_sparc`). The PDF itself gives V̄ = 0.05 and ωc_max = 20π only for its simulated example (Additional file 3, Fig. S2 caption), and the FFT length is in Appendix A, which was not available. The first-run values are the authors' reference-code defaults, held in one documented constant `metrics.SPARC_REFERENCE_DEFAULTS` ("reference code defaults, not project-tuned; swept in 5.1a"): amp_th 0.05, fc 10 Hz (omega_c_max 20π rad/s), padlevel 4, with nfft = 2^(ceil(log2 N) + padlevel) (`metrics.sparc_n_fft`). Source, as stated by the author (not read by Claude Code): github.com/siva82kb/SPARC, `scripts/smoothness.py`, commit 3650934, read 2026-11-01. The sweep is the author's step 5.1a (D-004 method); no project value is set.
- **Regression test against the reference docstring.** Gaussian speed profile exp(−5t²), t from −1 in steps of 0.01, fs = 100: the implementation gives −1.41403 to five decimals on 200 samples (`np.arange(-1, 1, 0.01)`, last t = 0.99), the reference value. With the endpoint t = 1.00 included (201 samples) it gives −1.41399, which differs at the fifth decimal; the cause is the sample count, not the discretisation. A reference-style calculation written from memory of the reference code (frequency grid spacing fs/(nfft−1), threshold index range, arc normalised by the frequency span) agrees with this implementation to 1e-15 on identical input for either spacing, so the grid spacing and the normalisation do not matter. The author should confirm the reference example uses 200 samples. Nothing was adjusted to match.
- **Points in the paper that bear on D-006 (recorded, not acted on):** (1) the paper recommends SPARC over LDLJ because LDLJ is highly sensitive to measurement noise and low-pass filtering does not fully fix it (the supporting analysis is in the Appendix, unread); the rationale above for choosing LDLJ is unchanged and both are now implemented side by side. (2) Smoothness is task-dependent and the paper advises against interpreting it for unconstrained, exploratory movement; relevant to climbing and to the hold-to-hold segmentation and minimum segment duration of D-018. (3) For position data its Table 3 proposes the jerk magnitude ‖d³x/dt³‖ for LDLJ, whereas Eq. 2 and this entry use the second derivative of the speed; they differ on curved paths such as a CoM trajectory. D-006 and ARCHITECTURE §4.5 are followed as written. (4) Eqs. 6 to 8 give event-based segmentation and a weighted average of per-segment values.

| Part | Parameter | Value | Meaning |
|---|---|---|---|

## D-028: Gap filling as implemented (occlusion_handling.py) — every choice behind D-007's three tiers
**Date:** 2026-11-03
**Decision:** Implement D-007's three tiers in `occlusion_handling.py` (step 3.2 in the author's plan labels) with the choices below. **No tier is validated.** The boundaries (under 5, 5 to 20, over 20 frames) stay as D-007 states them and are unvalidated heuristics; the hide-and-fill test that would test them (step 3.3) does not exist. Raw data is never modified: the module returns new objects (a filled copy, a per-frame flag in {observed, tier1, tier2, tier3, unavailable}, the method and, for Kalman fills, the position standard deviation) and carries the raw positions, confidences and gap causes through.
**Choices (every one is the project's own; none has a literature source):**
1. *Joint set:* the 12 body joints (shoulders, elbows, wrists, hips, knees, ankles). The five face points are not handled.
2. *Gap run:* consecutive frames with no usable position for that joint, whatever the cause (confidence below 0.5, or a detector drop); excluded frames (`validation/frame_exclusions.csv`, empty since D-027) are never filled and are walls: no observed frame beyond one is used and a gap touching one counts as having no bracketing frame on that side. Because a detector-drop frame is a gap for every joint, run lengths differ from the 3.1 events (which end at drop frames).
3. *Boundaries:* length 1 to 4 frames Tier 1, 5 to 20 Tier 2, 21 or more Tier 3 (`TIER1_MAX_FRAMES`, `TIER2_MAX_FRAMES`).
4. *Tier 1:* per-axis not-a-knot cubic spline (`scipy.interpolate.CubicSpline`, real timestamps) through observed frames only, 5 on each side (ARCHITECTURE §3 says 5 to 10; the lower end), at least 2 on each side, otherwise unavailable. Not clamped.
5. *Tier 2, Kalman:* constant-velocity filter per axis with a Rauch-Tung-Striebel backward pass (uses the frames after the gap; `tier2_causal=True` gives the forward-only filter), in a window of 10 observed frames on each side. Process noise (acceleration std) `sigma_a = sigma_d2 / dt^2` and measurement noise `sigma_m = sigma_d2 / sqrt(6)`, with `sigma_d2` the MAD-based scale of the second difference of the joint's own observed positions on consecutive observed triples, pooled over x and y (at least 3 triples, else unavailable). Initial state from the first two observed samples with the covariance they imply. A heuristic estimate (an upper bound on the noise); its sensitivity is untested. The position standard deviation of each filled frame is stored. **Point to know:** with near-exact observed anchors a smoothed constant-velocity filter is a cubic smoothing spline, so Tier 2 differs from Tier 1 mainly through the clamp and the uncertainty, not through a different path.
6. *Joint-limit clamp:* ARCHITECTURE §3 asks for human joint-limit constraints (max angular range). No angular limits are sourced in the repo, so none are implemented. Instead each limb joint of a Tier 2 fill is projected onto the 2D segment-length range seen in the same clip (min and max over frames where both ends are observed, for forearm, upper arm, thigh, shank) around its proximal parent. This stops a limb stretching or collapsing; it does not stop hyperextension. **A deviation from the architecture's wording, adopted by the author with the plan.**
7. *Mirrored estimation (Tier 2 alternative):* trunk joints only, and only if the other three trunk joints are observed on every frame of the gap: the lost joint's barycentric coordinates with respect to the other three (taken at the nearest earlier frame where all four are observed, else the nearest later) are applied to them at each gap frame (exact for an affine trunk). Not for wrists or ankles, which move independently in climbing. It was never used on the five clips (no trunk joint has a gap); synthetic tests only.
8. *Tier 3 (limb joints only):* stale: the joint's offset in torso lengths in a trunk-aligned frame (origin shoulder midpoint for arm joints and hip midpoint for leg joints, axis along hip-midpoint to shoulder-midpoint, scale = torso length) is taken at the nearest observed frame before the gap at which the trunk is available (else the nearest after it) and applied at every gap frame, so the joint follows the trunk's translation, rotation and scale. It is a placeholder, not an estimate: a planted foot stays on its hold in wall coordinates, not with the hips. By default it is excluded from per-limb metrics (`as_joint_series(include_tier3=False)`), as ARCHITECTURE §3 says. The reference-frame rule extends the plan (it needs the trunk to be available at the reference frame).
9. *Circular root:* **the issue that root-freeze is circular if the root joint is lost was stated by the author on 2026-11-03; it was not written anywhere in the repo before this entry.** Resolution by design: the four trunk joints are the root and are never Tier 3; a trunk gap of 1 to 4 frames is Tier 1, 5 to 20 Tier 2 (mirror when applicable, else Kalman), and over 20 is unavailable; trunk joints are processed first; a limb frame whose trunk is unavailable at that frame is unavailable, so nothing is frozen relative to something unknown. No instance exists in the five clips (trunk joints never fell below 0.5, 3.1); it is tested synthetically.
10. *Clip start and end:* a Tier 1 or Tier 2 gap that touches a clip start or end has no observed frame on one side and is left unavailable (no extrapolation). Tier 3 may use the observed side. A joint never observed is unavailable.
11. *CoM substitution not implemented:* ARCHITECTURE §3's statistical default limb position for Tier 3 CoM (e.g. about 40 degrees from the torso) has no documented value, and the working CoM (E-dL, D-026) already drops a lost limb's term. **Interplay:** E-dL gates limbs on the raw confidence at or above 0.5, which filled frames keep as raw values, so gap filling does not change E-dL; it affects velocity, LDLJ, the four-state classifier and the coverage of F, C and D. Whether filled frames should count for E-dL is not decided (D-025's revisit condition re-runs the CoM comparison after 3.2).
12. *Module boundary:* `occlusion_handling.py` imports only `metrics.py`; the run script, outputs and manifest are `evaluation/3.2/run_gap_filling.py` and `evaluation/3.2/output_full_lock1/` (new folder; `<clip>_filled.csv`, 5,886 frames by 17 joints with raw and filled values side by side, is gitignored and regenerable).
**Tests (no tier validated by them):** 26 synthetic known-answer tests (`tests/test_occlusion_handling.py`: boundaries 4/5/20/21, exact reproduction of a cubic and of a line by the spline, the arc beating linear interpolation, the Kalman fill on a line and a smooth path, the clamp, uncertainty growth, the exact mirror, exact stale offsets under trunk translation, rotation and scale, the circular-root cases, clip edges, excluded walls, translation, scale and left-right swap invariance, determinism, raw data unchanged) and 6 real-event tests on a committed fixture (`tests/fixtures/IMG_2412_first100_keypoints.csv`, first 100 frames of `validation/output/`, sha256 0c3da946fb2966883298fd07e9f034ccd5df11b235a1f69efcb68e03a30c0337): right wrist frame 64 (confidence 0.257) is a one-frame Tier 1 gap whose filled value lies near the interval of its observed neighbours and about 38 px from the raw low-confidence value (a 36 px outlier in y); right ankle frames 2 and 8 are Tier 1; right ankle 10 to 38 (29 frames) is Tier 3 with a constant trunk-frame offset; frames 41 and 42 (no person box in that run) are a Tier 1 gap for every body joint; the gap inventory equals the 3.1 events plus those drops. These record what the code does; there is no ground truth for a hidden position.

## D-029: Hide-and-fill test of the gap-filling boundaries and methods (step 3.3) — design, result, and what it does and does not show
**Date:** 2026-11-25
**Decision:** Record the design and result of the hide-and-fill test of D-007's boundaries (under 5, 5 to 20, over 20 frames) and of D-028's methods. **No tier and no boundary is validated, and none is changed by this entry.** What the test shows about the boundaries is stated below as an assessment; whether to change any boundary or default is the author's decision and is not made here (open question at the end).
**Design (every choice is the project's own; no literature source):**
1. *Truth:* the pose model's own confident output (confidence at or above 0.5), not ground truth. A trial is a span of consecutive frames hidden for one body joint, with 10 frames of context observed on each side and all 12 body joints observed over the span and context.
2. *Hidden lengths:* 1, 2, 3, 4, 5, 6, 7, 8, 10, 12, 15, 18, 19, 20, 21, 22, 25, 30 (the longest real gap is 30), and 40 and 60 (extrapolation beyond any real gap, marked `*` in the report).
3. *Trials:* the first start at frame 10, then a start every 25 frames, every body joint hidden one at a time; trials therefore overlap and are not independent. 38,604 trials over the five clips (1,560 to 2,112 per length). Several hidden spans are batched per `fill_gaps` call with at least 60 observed frames between them (the real `fill_gaps` is called; `evaluation/3.3/hide_and_fill.py`).
4. *Methods:* hold-last-position (baseline), spline, Kalman smoothed with the clamp on and off, Kalman causal with the clamp on and off, trunk-offset (Tier 3), and for trunk joints Kalman with mirrored estimation on. Clamp is reported for limb joints and mirror for trunk joints only.
5. *Error:* Euclidean pixels, per trial the mean over the hidden frames; torso-normalised columns divide by the clip's median torso length. Per length: median and interquartile range over trials. Paired comparison with hold: per-trial difference (method minus hold), median and share of trials where the method is better.
6. *Smooth and sudden classes:* the peak second difference of the TRUE position over the hidden span plus 2 frames each side, divided by the clip's median torso length; terciles within each (gap length, joint), pooled over clips; lowest third smooth, top third sudden, middle unlabelled. The cut points were written to `cutpoints.csv` before any fill was run; the rule was fixed in the script before the full run (development smoke runs looked at errors for plumbing only and the rule was not changed afterwards).
7. *Crossover:* the smallest tested length at which the median paired difference to hold is at or above zero. A bootstrap over the five clips (1,000 resamples, seed 0) is descriptive only: with five clips it is not a significance test.
8. *Tests:* 18 tests of the harness including a leakage test (the fill never sees the hidden truth) and a canary showing the leakage test fails when the mask hides nothing (`tests/`, commit `6e1b290`); the full suite passes (284 tests).
**Result (limb joints, all hidden trials pooled; paths in `evaluation/3.3/output_full_lock1/`: `report.md`, `summary_by_length.csv`, `paired_vs_hold.csv`, `crossover.csv`, `per_clip.csv`, `cutpoints.csv`, figures, `manifest.txt`; `trials.csv` is gitignored and regenerable; run at HEAD `6e1b290`, clean tree, outputs `55733d7`):**
- *Smoothed Kalman beats hold at every tested length* (median paired difference to hold negative at all lengths 1 to 60; no crossover through 60; at 4 frames -1.91 px with the method better in 81% of trials, at 20 frames -5.11 px and 76%, at 30 frames -6.03 px and 70%). This holds for the smooth and the sudden class (sudden: no crossover through 60).
- *Spline beats hold at every tested length too in the pooled set, but loses ground with length:* paired median -1.28 px at 4 frames and -1.95 px at 30; in the sudden class the paired median to hold turns positive at 30 frames (+0.29 px).
- *Smoothed Kalman has the lower median error than spline at every tested length*, for limb joints and for trunk joints, including at 1 to 4 frames where D-007 assigns the spline (limb, median at 4 frames: 2.6 px Kalman, 3.3 px spline; trunk 2.0 against 2.6). No length was found at which the two swap. This is read from the per-method medians in `report.md`; a direct paired Kalman-against-spline comparison was not computed.
- *Tier 3 stale offset is worse than hold at every tested length up to 30 frames* (paired median +0.74 to +1.60 px; better than hold in 33% to 48% of trials) and better only at the extrapolated 40 and 60 frames (-0.21 and -3.49 px). Its purpose in D-007 is to mark the position as unreliable, not to be accurate; this is a measure of accuracy only.
- *Causal Kalman is worse than hold from length 1 or 2 on* (crossover 1 pooled, 2 smooth class), so the offline smoothed filter is the only usable Kalman variant on this data.
- *The joint-limit clamp (segment-length range) changes medians by at most about 0.5 px at 20 to 30 frames and never made a median worse* (limb; larger at the extrapolated lengths in the sudden class, 36.3 against 32.8 px at 60 frames without it).
- *Mirrored estimation (trunk, artificial: the five clips contain no trunk gap)* is worse than plain smoothed Kalman up to 30 frames (e.g. 10.3 against 9.8 px at 30) and better only at the extrapolated 40 and 60 frames.
**Assessment of the boundaries (not a change):** (a) The 5-frame boundary between spline and Kalman is not supported by this test: the smoothed Kalman filter is already at least as good at 1 frame. Method and context are confounded: the spline uses 5 observed frames on each side (D-028 item 4) and the Kalman filter 10 (item 5), so the test cannot say whether the gain is the method or the extra context. (b) The 20-frame boundary: the Tier 3 stale offset is not more accurate than hold or than smoothed Kalman at 21 to 30 frames, the longest real gap, so accuracy alone does not support switching to it at 20; Tier 3 may still be wanted to flag unreliability. (c) Everything above is conditional on the truth being the model's own output and on gaps being hidden at times when the climber was fully observed; real gaps occur in hard poses and are likely harder, so errors here are probably understated, and the test cannot show how much.
**Limitations and caveats (every one):** (a) five clips of one gym, no ground truth: the "truth" is the model's own confident output; (b) trials overlap (start every 25 frames) and the effective sample is far smaller than the trial counts; (c) the bootstrap resamples five clips and is descriptive; (d) smooth and sudden are terciles of the test's own motion measure, not a validated classification; (e) hidden spans are chosen where all 12 joints are observed, unlike real gaps, which cluster in hard poses and often hide several joints at once; (f) 40 and 60 frames are longer than any real gap and are extrapolation; (g) mirrored estimation is tested only artificially; (h) spline and Kalman differ in context length (see above); (i) the error is in pixels in a single fixed-camera view (D-008) and says nothing about error in metres, nor about downstream metrics (smoothness, CoM); (j) a wrong keypoint above 0.5 confidence is "observed" and invisible here (D-028 limitation b); (k) the test measures position error, not whether a fill is plausible to a viewer.
**Open question for the author (not decided):** the test gives no support for the 5 and 20 frame boundaries and finds the smoothed Kalman at least as accurate as the spline at every length. Should D-007/D-028 be revised (for example one method below 20 frames, or Tier 3 kept only as a flag), or are the boundaries kept as they are until a larger test on the 4.2 footage? This entry changes nothing until the author answers.
**Source(s):** no literature source — engineering test design, validate empirically. Hide-and-fill is the validation D-007 names.
**Status:** proposed (the test is implemented and run; the result is not a validation of any tier)

## D-030: Proposed revision of the gap-filling tiers — smoothed Kalman for 1 to 20 frames, no spline tier, Tier 3 as an unreliable flag without a position
**Date:** 2026-11-25
**Decision (proposed; nothing adopted, nothing validated, no code changed by this entry):** if adopted, this supersedes the following parts of D-007 and D-028 and nothing else:
1. **One fill method for gaps of 1 to 20 frames:** the smoothed Kalman filter (constant velocity, RTS backward pass, context `tier2_context`, segment-length clamp on for limb joints) for every gap of 1 to 20 frames. The spline tier (Tier 1) and the 5-frame boundary are dropped. The 20-frame boundary stays as it is in D-007; it is an unvalidated heuristic (see "The 20-frame boundary" below).
2. **Tier 3 becomes a flag, not a position:** a limb-joint gap of more than 20 frames gets no guessed position (the stale-offset fill of D-028 item 8 is dropped). The frames carry a flag meaning "gap over 20 frames, position unreliable, none given" and are excluded from per-limb metrics by default (as `as_joint_series` already does for Tier 3, ARCHITECTURE §3). Proposed flag handling, for the author to confirm or change: keep the existing flag value `tier3` for these frames, so that "gap over 20 frames" stays distinguishable from `unavailable` (a gap that could not be filled for another reason, e.g. a clip edge). Trunk joints are unchanged (a trunk gap over 20 frames is already unavailable, D-028 item 9). **Said plainly: in the hide-and-fill test (step 3.3, D-029) the Tier 3 stale-offset position was WORSE than the hold-last-position baseline at every tested length up to 30 frames** (paired median difference to hold +0.74 to +1.60 px, better than hold in only 33% to 48% of trials), and better only at the extrapolated 40 and 60 frames. It was also worse than the smoothed Kalman at every length through 60. This is a measure of position accuracy only; the stale offset was never meant to be accurate (it follows the trunk), only to be a placeholder.
**Not covered by this entry (left exactly as D-028 has it):** mirrored estimation for trunk joints (D-028 item 7, default on in the code). In 3.3 it was worse than plain smoothed Kalman up to 30 frames, but only in an artificial test (the five clips contain no trunk gap), so there is no real instance and it is not decided here. Open question below. The Kalman noise estimate, the clamp, the clip-edge rule, the excluded-frame rule, and the causal option are unchanged.
**Evidence (all from `evaluation/3.3/output_full_lock1/` and `output_matched_context_lock1/`; five clips, 38,604 hidden-span trials; no figure below is new):**
- *Kalman against hold:* the smoothed Kalman beat hold-last-position at every length from 1 to 60 (limb joints, pooled; median paired difference -1.91 px at 4 frames, -5.11 px at 20, -6.03 px at 30; no crossover through 60).
- *Kalman against spline at matched context (D-029 addendum):* with the same context (5 or 10 observed frames each side) the pooled median paired difference (Kalman minus spline) at 1, 2, 3 and 4 frames is -0.2, -0.4, -0.5, -0.6 px (limb) and -0.2, -0.3, -0.5, -0.5 px (trunk), the Kalman median lower in 5 of 5 clips, identical at both contexts. **The difference at 1 to 4 frames is 0.2 to 0.6 px (0.001 to 0.003 torso lengths).** Context size changed either method by well under 0.1 px at the median, so the first run's context confound did not explain the gap.
- *Where the rule did not hold:* the pre-run survival rule (pooled median difference below 0 and Kalman lower in at least 4 of 5 clips) **failed in the smooth class at 1 frame (limb and trunk) and at 4 frames (limb)**: Kalman lower in 3 of 5 clips there, pooled differences still negative (-0.07 to -0.37 px). In the sudden class the advantage is larger (limb -0.6 to -1.1 px at 1 to 4 frames).
- *Post hoc, not pre-registered:* for trunk joints at 1 frame the median paired difference in clip IMG_2412 is +0.03 px (Kalman not better in that clip); this was read after the results and was not in the rule.
- *Real gaps:* in the gated-lock run (`evaluation/3.2/output_full_lock1/`) there are 178 body-joint gaps: 142 of 1 to 4 frames, 32 of 5 to 20 and **only 4 of more than 20 frames** (IMG_2412: 1, IMG_2417: 3; 102 joint-frames of 70,632); the longest real gap is 30 frames. The Tier 3 change therefore touches four events in five clips.
**Limits of this evidence (every one):** (a) the truth is the pose model's own confident output (confidence 0.5 or more), not ground truth; (b) the hidden spans were placed only where all 12 body joints were confidently observed, i.e. on easy frames; real gaps happen in hard poses and are probably harder, so every error here is probably understated and the ranking of methods may differ on real occlusions; (c) five clips of one gym, with trials overlapping (a start every 25 frames), so the effective sample is far smaller than 38,604 and a clip bootstrap over five clips is descriptive only; (d) the survival rule is the assistant's own and descriptive, not a significance test; (e) the matched-context difference at 1 to 4 frames is only 0.2 to 0.6 px, so the case for dropping the spline is mainly simplicity (one method, one fewer boundary), not accuracy; (f) the smooth-class rule failure at 1 and 4 frames and the IMG_2412 trunk result (post hoc) show the advantage is not uniform; (g) only 4 real gaps exceed 20 frames, so nothing about long real gaps is tested and the Tier 3 conclusion rests on the artificial hide-and-fill; (h) contexts other than 5 and 10, the noise estimate and the spline's end conditions were not varied; (i) position error in pixels in a fixed-camera view (D-008) says nothing about downstream metrics (smoothness, CoM, timing), which were not tested; (j) a wrong keypoint above 0.5 confidence is "observed" and invisible here (D-028 limitation b).
**The 20-frame boundary (stated plainly, not changed):** 3.3 does not support 20 frames as an accuracy cut either. The smoothed Kalman beat hold at 21 to 30 frames (paired median -5.11 px at 21, -6.03 px at 30) and had a lower median error than the stale offset there (limb, class all: 8.5 against 17.2 px at 21 frames; 11.6 against 21.5 px at 30). The reason to keep a cut at 20 and flag longer gaps is trust, not measured accuracy: Kalman error grows with length (median 7.9 px at 20 frames, 11.6 px at 30, and larger in the sudden class), long real occlusions are probably harder than the hidden easy spans, and no real long gap has been checked. **Alternative not adopted here:** smoothed Kalman up to 30 frames (the longest real gap) with the flag only beyond that. If the author prefers it, this entry would be changed before adoption.
**Consequences if adopted (a separate, not yet started code step, see below):** the spline is no longer used in production (it can stay behind `force_method` for the evaluation scripts); Tier 3 limb frames carry no position, so the Tier 3 stale position no longer serves as the parent in the segment-length clamp of a neighbouring limb joint (a behaviour change to be tested: the clamp is skipped when the parent has no position, as it already is for an unavailable parent); the gap tables of `evaluation/3.2/` (Tier 1 counts) are reshaped; the real-event tests that expect Tier 1 and Tier 3 positions (`tests/test_occlusion_real_events.py`, `tests/test_occlusion_handling.py`, about 22 assertions on the tier flags and positions) change; availability for gaps near a clip edge must be checked (the Kalman needs a noise estimate from at least 3 observed triples, the spline did not). ARCHITECTURE §3 is not updated while this entry is proposed.
**Code change: NOT made.** The change touches the driver, the flags, the clamp interplay, the run script and a third of the module's tests, so it is not small; it is logged as a separate next step to be done only after the author adopts this entry or asks for it.
**Rationale:** one method with the best median at every tested length is simpler to describe, to test and to defend than three tiers with boundaries that 3.3 did not support; a stale position that was measurably worse than doing nothing (hold) should not enter any computation; flagging the few long gaps (4 of 178) is honest about what is not known. This is a proposal on weak evidence, not a validated improvement.
**Source(s):** no literature source — engineering decision from this project's own hide-and-fill results (D-029 and its addendum), validate empirically; Kalman and RTS as in D-028 item 5.
**Status:** proposed
**Superseded by:** — (it would supersede the boundary, Tier 1 and Tier 3 parts of D-007 and D-028 only if adopted; their statuses stay proposed until then)
